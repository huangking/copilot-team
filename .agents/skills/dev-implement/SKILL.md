# Dev：按规格实现

## 何时使用

- 已有 `docs/specs/<id>.md`，需要落地代码
- 需要修复 Test 报告里的失败项
- 需要在不改变外部行为的前提下重构

## 流程

1. **读规格与代码**：读 spec、`AGENTS.md`、目标模块及其测试。确认命令可用。
2. **写计划**：`docs/plans/<id>.md` —— 改动点、取舍、验证命令、风险。
   计划不超过 1 页；超过说明任务该拆。
3. **测试先行**（能做到时）：先写/改一个会失败的测试，确认它因正确的原因失败。
4. **最小实现**：只改与 AC 相关的代码；复用既有模式；不顺手重构无关代码。
5. **自检**：
   - 运行 lint / typecheck / 目标测试
   - 检查 diff：有没有调试代码、无关格式化、误改的配置
   - 对照每条 AC，确认有对应验证
6. **交付**：更新 `docs/plans/<id>.md` 的"验证结果"，把命令与关键输出贴给 Test。

## 计划模板

````markdown
# <feature-id> 实现计划

## 改动点
| 文件 | 改什么 | 为什么 |
|---|---|---|

## 关键取舍
- <!-- 选了 A 不选 B 的原因 -->

## 验证命令
```bash
<TODO>
```

## 风险
- <!-- 兼容性、性能、数据迁移 -->
````

## 约束

- 不改验收标准；发现 AC 不可实现 → 回退 PM。
- 不跳过失败测试；不 `--force`、不注释掉断言来"变绿"。
- 不提交密钥；不 `git push`；不改发布分支。
- 不修改 `.github/workflows/**`、`infra/**`（那是 DevOps 的边界）；需要改就提给 PM。
- 修复 Test 报告时，一次只修一个失败项，并说明根因。

## 输出

- 代码 diff
- `docs/plans/<id>.md`（含验证命令与结果）
- 交给 Test 的摘要：改了哪些文件、怎么跑、预期结果、已知风险
