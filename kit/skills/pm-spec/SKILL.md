# PM：需求 → 规格

## 何时使用

- 收到新功能、缺陷修复、重构请求，但还没有可执行的规格
- 需要判断"这件事到底做不做、做到什么程度"
- 需要把规格拆成 Dev 可执行的任务

## 流程

1. **先读再问**：读 `AGENTS.md`、相关 `src/`、已有 `docs/specs/`、最近的 issue/PR。
   能从代码里查到的事实，不要问用户。
2. **只问用户能决定的事**：范围取舍、优先级、兼容性承诺、上线时间。
   一次最多问 3 个问题，附上你的建议选项。
3. **写规格文件**：`docs/specs/<id>.md`，用下面模板。
4. **自检**：每条验收标准都能被"一条命令 / 一个测试 / 一次明确的人工检查"验证吗？
   不能就改写，直到能。
5. **拆任务**：每项 ≤ 半天，标依赖与可并行的部分。
6. **交付**：把规格路径 + 一段 5 行摘要交给 Dev；不要复述全文。

## 规格模板

```markdown
# <feature-id>：<一句话标题>

## 背景与目标
<!-- 为什么做；完成后用户/系统有什么不同 -->

## 非目标
- <!-- 明确不做的事，避免范围蔓延 -->

## 验收标准
| ID | 标准 | 验证方式 |
|---|---|---|
| AC-1 | <!-- 可观察的行为 --> | `make test-xxx` / 手工步骤 |
| AC-2 | ... | ... |

## 边界与错误场景
- <!-- 空输入、超时、并发、权限、回滚 ... -->

## 任务拆分
| # | 任务 | 依赖 | 负责角色 |
|---|---|---|---|
| 1 | ... | - | Dev |
| 2 | ... | 1 | Test |

## 风险与回滚
- 风险：
- 回滚：

## 开放问题
- [ ] <!-- 需要人决定的事 -->
```

## 约束

- 不改 `src/**`、`tests/**`、CI、部署配置。
- 规格里不写实现细节（除非是硬约束，如"必须复用 X 模块"）。
- 验收标准只写"可观察的结果"，不写"用了什么技术"。
- 需求含糊时，先给一版带假设的规格，再把假设列在"开放问题"里，而不是空转。

## 输出

- `docs/specs/<id>.md`
- 给 Dev 的交接摘要（≤ 5 行）：目标、AC 数量、关键约束、建议起点
